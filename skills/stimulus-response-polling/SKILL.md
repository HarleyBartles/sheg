For a new request that starts with material and a question, first use the [study-design skill](../study-design/SKILL.md). It guides the conversation about what to ask and whose perspective matters before turning the accepted human-language design into Sheg inputs. This skill remains the detailed guide for cohort contracts and harness operation.

The study unit is a bounded text stimulus, a task with typed response options, and a frozen set of distinct respondents. A study has one or more arms. Each arm couples its stimulus sources, ordered items, tasks, and presentation mode. A run applies every respondent to every arm once. Repeating the same respondent, stimulus, and task is not a larger or more independent sample.

Before using a tool, establish the study question and requested stage. Use `poll_capabilities` for the current semantic capability catalogue. A task defines its response type, instructions, and optional task-specific history policy. Choice uses stable option IDs and can include `unanswerable` when the task can lack sufficient evidence. Never expose answer keys or other arms to the model. Keep arm and rerun changes explicit; use shared comparison keys only when outcomes should align. Prefer `sequence` for bounded item-then-task studies; use `graph` when conditional exposure or respondent routing is part of the study.

`poll_measure_packets` measures explicitly supplied draft inputs and does not call inference. Paired mode joins same-index variants, broadcasts singleton dimensions, and rejects unequal multi-valued dimension lengths; Cartesian mode measures every combination. `poll_preview` shows all branches from a manifest without a cohort or provider call. `poll_check` validates and fingerprints inputs; `poll_preflight` measures every reachable packet for each supplied provider; `poll_trace` follows an explicitly scripted Choice or typed response route. These operations do not call inference. Run preflight when the complete journey and frozen cohort are ready. A trace needs explicit outcomes for a defined scenario. If outcomes are missing, ask for them or explain what cannot be established; never invent respondent behavior.

For every new run, validate the exact manifest, cohort, provider, and budgets with `poll_check` before `poll_start`. Before starting, report the provider, arm count, number of distinct respondents, total respondent-arm cells, call limit, output location, and hosted spend caps. For paid Jev runs, require explicit authorization for this study and these caps. Read the run guidance before recommending or starting inference.

The meaningful simulated unit is a distinct respondent-profile, stimulus, and task cell. Provider attempts are retries, not new respondents. Compare separate runs only with `poll_compare_runs`, which requires the same exact frozen cohort and aligns typed outcomes only when task meanings match. Reports can group by declared archetypes and variations with their denominators; do not infer demographic categories that are absent from the cohort. Reports describe simulated typed responses and optional answer-key scoring, not human readership, statistical significance, causal lift, or real-world accuracy. This skill can guide generic archetype authoring and stimulus-specific respondent creation; it does not rewrite the stimulus text.
