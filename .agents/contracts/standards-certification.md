# Operating standards certification

Sheg subscribes to the immutable definitions listed in the v2 [operating-standards.json](operating-standards.json). `unslop`, `playbook-composition`, and `runbook-composition` retain their Agent Asset Marketplace source at commit `88c02ec6804fd695e43bf6a632c61014a21738f4`. `gitflow` and `semver` use the published definitions at `12c86626f80cad1a2ac05b2f6690c882a3d5959a`. Each entry identifies its definition and this certification; migration of the record shape does not upgrade the existing definitions.

The repository's adoption and routing decision is recorded in [ADR-0034](../../docs/decisions/0034-adopt-routed-agent-operating-standards.md).

The implementation lives in `.agents/unslop/`, `.agents/playbooks/`, and `.agents/runbooks/`. Root [AGENTS.md](../../AGENTS.md) routes agents to this subscription and certification; the [runbook and playbook policy](../doctrine/repo-runbook-policy.md) describes the lifecycle and concern routes.

Sheg gives the loose upstream playbook standard a local implementation: every concern guide uses Applicability, Method, Constraints, Verification, References and routing, and Maintenance in that order, as defined in the policy. Gitflow owns branch and release routing, version alignment owns release identity, and source quality owns implementation and review concerns. Their methods include the capabilities, decisions, constraints, and evidence needed for those concerns; empty capability inventories are omitted. Each is reached from implementing and PR stages and links back to those applicable lifecycle procedures.

When authoring or changing a playbook, review its applicability against actual repository work, trace its method through the current commands and policy owners, check whether its constraints prevent the relevant mistakes, and assess whether its verification establishes the stated result. Inspect stage routing in both directions and maintain the guide when those dependencies change. The author maintains this certification in the same change; PR review independently assesses its semantic claims. Uniform structure supports review but does not establish usefulness or agent readership.

Agents complete the [source-quality method](../playbooks/source-quality.md#method) checks when implementing or reviewing source changes. It defines an Unslop profile, names `.agents/unslop/` as the canonical location, and links each corrective guide beside mandatory inspections of owners, execution paths, reuse, and transaction boundaries. Stage routes require concrete findings before editing and a review of the final diff before readiness. Findings name source files or symbols and justify exceptions in the working chat or PR; saying profiles were read or applied does not satisfy the method. These are procedural review obligations, not mechanically enforced proof of compliance.

For documentation changes, the source-quality method also routes [README placement](../unslop/readme-as-default-documentation.md) and the policy's documentation audiences. Agents identify the reader task and owning document before editing; reviewers assess each README addition's front-page purpose, human versus agent instruction ownership, current-truth wording, and routes to the relevant guides. Live guidance excludes development history and receipts. The guard retains distinct mistake evidence without claiming independent recurrence or proven effectiveness.

When a distinct mistake matches a profile, the agent records a durable reference in that profile, checks whether prior evidence is independent, and assesses whether the guard was reachable, followed, and useful. A successful change alone does not establish profile effectiveness. Narrow, consolidate, revise, or retire profiles only when later evidence supports that choice.

`npm run guidance:check` validates subscription metadata, local Markdown links, the required ordered and populated sections of every playbook, inventory registration, applicable stage links and their inbound routes, and the source-quality profile routes. It checks commit syntax rather than fetching or establishing upstream provenance; pin changes require inspecting the immutable source definition. Reviewers judge concern category, method usefulness, current policy accuracy, evidence sufficiency, and maintenance obligations. These mechanical checks do not establish readership or behavioral effectiveness.

## Gitflow

Sheg implements the Gitflow pledge through [branch and release routing](../playbooks/gitflow-branch-and-release.md), the [PR runbook](../runbooks/pr.md), and the [release guide](../../docs/guides/releases.md#branches-and-promotion). [ADR-0037](../../docs/decisions/0037-adopt-gitflow-and-semver-cadence.md) records fit, adoption, and joint version cadence. `develop` owns integration and ordinary feature bases/targets; `main` owns stable releases. `release/<version>` starts from integration and accepts only bounded release preparation/stabilization; `hotfix/<version>` starts from released stable state. Promotion and reconciliation use merge commits; ordinary feature PRs may squash. Reconciliation preserves continuing development, active planning custody, and fixes in every affected active release branch.

Agents verify current remote refs, source/target SHAs, PR heads, merge results, and hosting rules through Git and available hosting tools before relying on them. `.github/workflows/ci.yml` validates non-draft PRs into `develop`, `main`, and `release/**` and rejects ordinary feature sources targeting `main`. That source-name check does not prove branch origin, merge method, scope, or reconciliation completeness; review and remote merge evidence own those judgments. `.github/workflows/release.yml` checks tag source ancestry before stable publication. Hosting permissions and required checks must be inspected live, not inferred from this certification. Revisit certification whenever routes, merge methods, active release policy, hosting rules, or cadence change.

## SemVer

Sheg is one independently versioned Codex-plugin product. The [release guide's compatibility and version policy](../../docs/guides/releases.md#version-policy) identifies the current public surfaces used to classify changes, initial-development behavior, and independent datastore/payload authorities. Maintainers classify compatibility and intended release scope during review. The absence of a general `0.y.z` stability promise does not remove Sheg's explicit supported datastore preservation guarantees. No future `1.0.0` guarantees are declared as a prerequisite to adoption.

Root `package.json` is the only authored product version and remains private. `scripts/build.ts` invokes version propagation into both lockfile root fields and `plugin.json`, bundles the MCP runtime identity from package metadata, and generates `plugins/sheg/` including its package and plugin manifests. `plugin.template.json` is version-free; its generator rejects an independently authored version. `npm run verify` compares those maintained generated outputs with a disposable build without rewriting checkout files. The manifest generator and packager reject malformed identities outside Sheg's stable/positive-dev/positive-rc subset. `npm run plugin:package -- --validate-only` validates current manifests; stable tagging additionally requires matching `vMAJOR.MINOR.PATCH` identity. Tagged source remains immutable release truth and the self-contained ZIP is its artifact. Dependency, SQLite-schema, and payload-contract versions remain separate authorities.

Each ordinary integration merge, including documentation/tooling, allocates one distinct `dev.N`. Authors propose the intended core and next number in the PR; review refreshes current `develop` and requires stale or duplicate proposals to be reallocated, rebuilt, and reverified. A new core begins at `dev.1`, and a PR's internal commits share one proposal. Changed qualified candidates advance `rc.N`; unchanged-source reruns retain it. Stable promotion rebuilds without a suffix. Reconciliation retains stable identity at the released product baseline or advances the existing intended next-release checkpoint when work continues. Restored active planning artifacts alone do not start a development line. Development and candidate identity do not imply qualification, tags, or publication.

Parity and package behavior tests establish generated identity consistency, malformed-input rejection, checkout preservation on drift, and packaged runtime behavior. Those checks cannot establish one authored authority from equality alone, semantic bump correctness, checkpoint uniqueness against a moving remote head, candidate qualification, or reconciliation meaning. Review traces authorship and these decisions through the playbooks and release guide. Maintain this certification when public contracts, authored/version destinations, build inputs, drift controls, candidate procedures, or publication paths change.
