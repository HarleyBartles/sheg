# Sheg v0.3.0: durable requests and reusable respondent evidence

Status: approved by the user on 2026-10-01. Date: 2026-10-01. Repository baseline: `origin/develop` at `3c5b2f00037634e24b5a4766d37004a699c43d2c`, version 0.2.0.

This specification consolidates the agreed design sketch. It governs a release roadmap whose implementation plans are written just in time. It is not an implementation plan or permission to execute paid inference, publish a release, or delegate work.

## 1. Outcome and product boundary

A user brings material and a question. Their agent uses Sheg to run the simplest investigation that answers it, inspect the evidence, and construct the next useful request. A simple investigation can be one question; a deeper one can combine exposure, independent questions, dependent questions, and conditional journeys.

The agent has two starting points. When the user knows what to ask, fulfil that request without a compulsory design exercise. When the user has tentative ideas, help establish what they want to learn and recommend the right questions, perspectives, and journey. Complexity earns its place through the answer it helps the user obtain.

Sheg supplies typed execution, durable evidence, focused machine-readable tools, and skills explaining their use. The agent owns relevance judgments, research design, interpretation, and explanation to the user. Sheg does not choose what counts as an interesting respondent, prescribe confidence cutoffs, generate editorial conclusions, or decide whether partial results answer the user's question.

### Release demonstrations

The first delivered capability is small and complete: submit one typed question, close the originating chat, return in another chat using the same datastore, discover the run, and retrieve its answer.

The integrated release demonstration is the section-three investigation:

1. Run an authored journey that records departure at section three and a lost-interest reason. Departure alone must not be treated as that reason.
2. Query the recorded evidence and retrieve the qualifying respondents' exact section-three contexts and identities.
3. Ask new independent typed questions at those recorded states without re-executing sections one and two.
4. Run an intentional variant using the same perspectives and section-three material with earlier history removed. Selection rationale and source lineage remain outside respondent input.
5. Offer agent-authored material candidates, inspect the selected exact material, and use those respondent/material references in a further request.

The agent explains the answers and recommends a next action. These are simulated typed judgments, not evidence of observed human readership or causation.

## 2. Scope, alternatives, and non-goals

The epic covers request-driven execution, optional inspection, durable local runs, cross-chat worker lifetime, discovery, result queries, reusable contexts, independent questions, authored source linkage, controlled deletion, and shipped agent guidance. Codex remains the supported plugin harness; standalone CLI behavior must be accounted for without expanding the release into support for every harness.

The selected approach replaces restrictive boundaries where necessary:

| Approach | Consequence | Decision |
| --- | --- | --- |
| Keep manifest/cohort files and add clone-study operations | Agents reconstruct files and duplicate studies to ask about recorded turns | Reject as the required MCP workflow; optional import may remain useful |
| Add a separate mutable study/session registry above runs | More creation and ownership steps before useful execution | Reject; a run records an accepted request over reusable inputs |
| Accept rich requests and persist immutable evidence in SQLite | Agents submit questions and reuse recorded pieces through identifiers | Adopt |

SQLite is the authoritative store. Compared with ad hoc run files, it supports transactional changes, relationship integrity, explicit queries, and concurrent local readers/writers without requiring a separately administered database server. Files remain useful for exports and implementation-owned artifacts.

Out of scope are Kev integration, hosted multi-user storage, cross-computer sync, a generic experiment platform, automatic editorial cutting, free-form respondent explanations, a new continuous scalar primitive, and a required export/import product. Existing material, questions, and response types should be reused where they meet the contract.

SHEG-9 and SHEG-10 remain cancelled. No interpretation-checking subsystem, model-determinism research, replicated provider benchmark, compulsory diagnostic battery, universal uncertainty score, confidence-driven routing, speculative branch execution, spend ceiling, cumulative billing, or reconciliation is a prerequisite. Accept published System One behavior and verify Sheg's own integration.

## 3. Domain contracts

These are responsibilities, not a demand for one table, class, registry, or MCP tool per row. Agents can supply inline definitions without registering them first.

| Concept | Contract |
| --- | --- |
| Respondent | Stable identity with a frozen authored perspective. A cohort is a selection of respondents |
| Material | Frozen authored content with stable identity and source provenance |
| Decision context | Immutable respondent-visible state before a question set: perspective, in-scope material, and intentionally supplied history |
| Question | Authored wording and a Choice, Score, or Noul response contract |
| Question set | One or more independent questions applied to the same context |
| Evaluation | Applying questions to one context, retaining per-question typed answers and execution evidence |
| Journey | Authored exposure, evaluation, and routing steps that produce respondent-specific contexts |
| Run | Durable server-owned record of one accepted execution request, resolved inputs, progress, results, and lineage |

Study remains ordinary user language. It is not an additional entity that must be created, registered, cloned, or preserved before an agent can run a request. Many run IDs are expected. A new question set or intentional input change creates a new run; explicit resume continues unfinished work under the same run identity.

An identifier must resolve without interpreting report prose or replaying a journey. Turn references distinguish respondent, stage/question occurrence, and exact context. A repeated visit to the same authored stage must not become an ambiguous reference. Runtime identifiers resolve within a configured datastore; another installation or computer does not automatically hold the same records.

## 4. Request acceptance and optional inspection

The MCP accepts rich schema requests combining inline authored definitions with references to recorded respondents, material, questions, turns, and contexts. Requests express a simple evaluation, a finite journey, or a follow-on. Manifest and cohort files, a create-study call, and primitive-registration calls are not prerequisites.

Execution performs schema validation, reference resolution, authored-rule validation, context admission, and execution-limit checks. Acceptance freezes the resolved inputs and persists a readable run record before returning `runId`. Provider inference runs after acceptance, independently of the tool call. A quick invalid-request error returns directly; a failure after durable acceptance is visible on that run. A worker-launch failure retains the accepted record with an explicit non-running failure and an explicit recovery path. Startup and status reads do not retry that launch. There must not be an undiscoverable accepted run.

Retries of the same identified submission must not start duplicate paid work after a lost acceptance response. A deliberately repeated evaluation remains a new submission. Reusing a submission identity with changed authored inputs or execution settings is an explicit conflict, not permission to replace the run or start another one. The JIT plan specifies the identity schema and retention without confusing retries with intentional repeats. Retrying an unchanged submission uses its already accepted frozen selection, not new matches from a source run that has since progressed.

Consolidate `poll_preview`, `poll_check`, and `poll_preflight` into one optional request-inspection surface. It accepts the same request shape as execution and shares resolution and validation. Agents request relevant projections:

- Intended respondents, material, wording, routes, and history/context choices.
- Reference validity, supported features, provider fit where verifiable, and execution bounds under the configured physical-attempt limit.
- Structured problems located in the request, with actionable error information.

Inspection makes no inference calls and creates no run. Direct execution does not require an inspection call. Draft packet measurement and scripted journey tracing remain separate only where they serve distinct authoring needs; neither becomes a mandatory step for ordinary requests.

Inspection of a progressing source reports current matches, source status, and selection completeness. For example: 12 matches, source still running, more may match later. An interrupted or failed source does not become complete merely because it stopped. Execution freezes selector matches at acceptance. An agent can instead submit explicit respondent/context references to retain a previously inspected selection. No separate resolved-request object or reservation is needed.

## 5. Evidence queries and follow-on composition

Provide discovery by date, execution status, optional agent-supplied labels, and referenced material. Return compact machine-readable summaries and run IDs. Labels are optional, including for one-question runs. Multiple matching runs remain visible for the agent to resolve with the user.

Focused queries and detail projections expose:

- The accepted request and frozen definitions.
- Respondents, perspectives, material, questions, and source identities.
- Recorded turn contexts, supplied history, exposure, route outcomes, and occurrence.
- Typed answers, full available distributions, available provider confidence, counts, reach/completion denominators, and aligned comparison evidence.
- Execution progress, failures, physical attempts, provider/model identity, compiler/context fingerprints, and lineage.

Results are bounded and paginated with explicit completeness information. Reusable identifiers are accepted directly by subsequent requests. An agent must not fetch a whole report to reconstruct a few selected contexts. Filter/query expressions can combine explicit criteria over recorded evidence; Sheg applies the criteria, while the agent chooses their meaning and relevance. The MCP is not a direct SQL interface.

Respondent selection and model-visible context are separate. Selecting an earlier answer does not put that answer, the reason for selection, or its source run into the new model input. Context reuse has these defaults:

| Request intent | Model-visible context |
| --- | --- |
| Ask at selected recorded turns | Each respondent's exact original pre-question context |
| Ask selected respondents about supplied material afresh | Saved perspective plus supplied material; no earlier journey history |
| Continue from selected turns | Recorded context and answers, followed by explicitly supplied next steps |

Explicit variations can remove selected history, replace/rearrange material, change questions, or change perspective. Derive a new immutable context and record the intended change; never edit the source context. Removing earlier history for a fresh section-three request also excludes incidental earlier exposure/order metadata that would disclose it. Do not embellish a perspective with an outcome.

Persist the exact original model-visible state, or immutable inputs and compiler identity sufficient to reproduce it exactly and verify its fingerprint. Approximate narrative reconstruction is insufficient. A follow-on uses each respondent's own state rather than one shared cohort history.

Provider route, served model identity where available, and compilation semantics are part of comparison provenance. Alias/model-version drift must remain visible; do not label changed-provider execution as an input-only comparison. Different questions do not become numerically equivalent because they share a context.

## 6. Independent questions and provider execution

Independent questions receive the same pre-group respondent state. They do not receive sibling answers, other respondents, future material, or unreached branches. One, two, five, or another supported number of questions is the same capability. Explicit dependent follow-ons can use completed answers, including selected answers from a completed group.

Batching is Sheg's concern. Use supported multi-question requests where useful and split into smaller requests when necessary, preserving the exact context and independence. Splitting changes transport, not question meaning. Return individual typed answers and physical-attempt evidence. Shared request evidence is recorded once and linked to its answers.

Inspect/admit the actual physical packets. An individual context/question that cannot fit fails explicitly. Never silently trim material, prune history, rewrite questions, or switch provider. Every physical attempt, including retries and failed/interrupted requests that may have reached the provider, counts against `maxCalls`. Journey decision bounds remain distinct from physical-attempt bounds.

Jev BYOK is primary. Local inference remains supported with its own capabilities and fit limits; its limitations do not define the global product contract. Unsupported features are reported for the configured provider. Exact route wire support must come from provider evidence, not analogy between Jev routes.

The current repository blocks native TypeSafe inference because context admission is unverified. This spec does not silently remove that guard. A relevant JIT plan must establish a supported Jev execution strategy with valid admission evidence; automatic splitting may preserve independence without native multi-question transport. If the accepted workflow cannot be delivered on a supported route, report the release gap rather than changing the product contract or testing model determinism. Paid smoke tests require separate authorization.

## 7. Source-linked offered choices and typed interpretation

The agent decides what a bit of material means for the user's question, chooses its units, and supplies authored candidates. Sheg preserves exact offered text, source identity/digest, and explicitly supplied boundaries. An answer links the selected candidate to reusable material references resolving to that original text. No paragraph-only boundary, decomposition-advice tool, or automatic cutting is required. A no-fit option is supplied when the study calls for it.

Choice selects among offered candidates. Score represents an authored ordered rubric with its expected level and distribution. Noul retains its truth probability. Missing confidence remains missing; probability is not confidence; mean Noul probability is not a count of yes answers. Distinguish respondent disagreement from diffuse individual answers through inspectable evidence, not a universal verdict.

An ordered Score rubric about stopping position is a judgment on that rubric, not observed percentage read. A staged journey can record its simulated first threshold crossing; derived positions use declared stage boundaries. These are different questions, taught through skills rather than a new scalar primitive.

Bad, unavailable, or out-of-scope references fail explicitly. Do not silently substitute changed text. Source attribution is an offered typed answer, not access to internal model reasoning.

## 8. Local datastore and execution lifetime

Resolve one datastore root at server startup, allowing an explicit `SHEG_DATA_DIR` override and using the harness's persistent plugin data directory by default. Codex plugin integration must verify the required `PLUGIN_DATA` capability in supported harness versions. Define a stable OS user-data fallback for standalone execution or unavailable harness data support; never fall back silently to package cache, current working directory, a chat folder, or a repository.

Store authoritative records in `sheg.sqlite`. Use short transactions and WAL mode with bounded write-contention handling on supported local filesystems. Provider calls occur outside transactions. Related answer/progress changes are atomic. Multiple local MCP/worker processes can share the root; database locking does not replace explicit execution ownership. Active multi-computer access over a network share is not a promised capability.

The MCP accepts and inspects work. A local execution worker has a lifetime independent of its originating MCP connection, chat, and harness process. An asynchronous promise inside the MCP process is insufficient. The JIT plan chooses the worker topology and validates supported-host behavior. No always-on startup service or automatic resumption is implied.

| Event | Required behavior |
| --- | --- |
| Accepted request | Persist frozen inputs and identity; launch/assign execution and expose status; a launch failure remains visible without automatic startup retry |
| Chat or harness closes | Existing worker continues; this is not cancellation |
| Isolated provider failure | Retain saved answers and continue unaffected work with satisfied prerequisites |
| Shared failure, such as unusable credentials | Stop affected execution; expose the reason and saved progress |
| Present but unreadable Jev credential | Distinguish it from a missing key; accept valid odd-length UTF-8 and Sheg-written UTF-16LE blobs, and give a safe setup-helper repair instruction without exposing token bytes or value |
| Worker crash or host shutdown | Preserve saved work; unfinished execution becomes explicitly resumable |
| Harness starts or status is read | Expose/reconcile stored state without launching interrupted work |
| Explicit resume | Claim unfinished work under the same run identity and remaining authorized budget |
| Explicit cancellation | Stop further dispatch, settle in-flight work, and record cancelled state |

Cancelled and completed runs cannot silently become running again. A changed question/context/provider configuration is a new request, not resume. Credential rotation need not change execution identity. No saved answer is repeated as part of ordinary recovery. Calls with uncertain provider completion conservatively consume reserved attempt allowance; recovery cannot manufacture remaining budget.

Queries distinguish completed answers, unanswered work, failures, blocked prerequisites, cancellation/interruption, and branches never reached. Failure does not manufacture an answer or permit dependent work to guess one. Run-level status cannot conceal these distinctions. The agent assesses usefulness.

## 9. Retention, deletion, and integrity

Retain runs until explicitly deleted. Provide MCP deletion operations with a dry-run option returning intended scope, affected records, dependencies, and shared data that will remain. Dry run does not mutate; it is optional rather than an additional approval ceremony. Actual deletion revalidates dependencies and acts transactionally within its declared scope.

Each retained follow-on keeps the frozen inputs/evidence needed to interpret and reuse it. Internal storage can be shared. Deleting a source run reclaims only data no retained run needs; including dependent runs requires explicit scope. Retained lineage may identify a deleted source, but must not present it as a live resolvable run. No surviving result/context/material reference becomes dangling.

Running work cannot be removed underneath a worker. Stop and settle it through the execution lifecycle first. A stale dry run cannot authorise deleting newly created dependants outside the requested scope. Manage any external artifact cleanup recoverably without making files a competing authority.

Sheg manages integrity, unreferenced-data reclamation, and database optimisation. Agents choose domain records to delete and can inspect storage usage; they do not edit SQLite or clean backing files themselves. Plugin-managed data can be removed on uninstall, so durability across plugin updates is not a promise of survival across uninstall or machine loss.

## 10. Ownership, distribution, and pre-v1 evolution

| Source boundary | Responsibility |
| --- | --- |
| `src/domain/` | Typed definitions, context/question semantics, identities, journey and selection rules |
| `src/application/` | Shared request resolution, acceptance, query projections and execution coordination |
| `src/providers/` | Verified route capabilities, admission, wire mapping and attempt evidence |
| `src/infrastructure/` | SQLite persistence, worker/process ownership, recovery, credential and artifact support |
| `src/entrypoints/` | Thin MCP/CLI schema boundaries over application operations |
| `skills/` | Canonical guidance for design, interpretation, query and follow-on composition |
| `contracts/` and `dist/` | Generated schemas and packaged runtime/skills produced from canonical sources |

Keep these boundaries focused rather than adding a catch-all study or platform module. Packaging must include the runtime/dependencies needed for SQLite and independent workers without requiring users to build the plugin themselves. Source, generated schemas, shipped skills, installation instructions, and actual tool contracts must agree.

Sheg has one user and is iterating quickly. No backward compatibility is offered below v1. Tool contracts, manifest/checkpoint formats, and database schemas may change without compatibility shims or migrations. Do not create legacy import, dual execution paths, or migration machinery solely to preserve an older version. JIT plans identify breaking changes and any required reset/setup instructions. This is not a requirement to retain the old interface or migrate old records.

Integrity and retention contracts apply to records supported by the current version: ordinary deletion cannot break retained follow-ons, and execution cannot mutate its frozen inputs. Changed source files must not be needed to interpret a newly frozen run. These runtime guarantees do not promise cross-version storage compatibility.

Keep secure Jev credentials in the existing supported vault mechanism. Keys never enter run requests, stored payloads, exports, process arguments, or MCP responses. Do not expand secure-store or harness platform support by implication.

Consequential architecture decisions require individual ADRs and index updates. Where this epic supersedes an accepted decision, add a superseding ADR rather than rewriting its history. JIT plans identify the affected records and perform that work with the implementing change; this spec is not an accepted ADR.

## 11. Release acceptance

The following are behavior obligations, not requests for tests that mirror wording or implementation. Use focused integration/behavior evidence and the repository gate where appropriate; no tautological or change-detector tests.

| Acceptance area | Observable result |
| --- | --- |
| Cross-chat execution | One-question run survives originating chat/harness closure and is discoverable/retrievable through a new connection |
| Durable acceptance | Returned run ID is immediately readable; frozen inputs survive source-file changes and restart |
| Submission retries | A lost acceptance response does not duplicate an identified submission or re-resolve its frozen selection; changed inputs under that identity conflict; intentional repetition remains possible |
| Explicit recovery | Startup/status never resumes interrupted work; resume preserves saved answers, identity and attempt allowance |
| Partial evidence | Failures and unreached work remain distinct; unaffected work progresses and dependent work never invents prerequisites |
| Concurrent ownership | Multiple local connections can query the store without duplicate execution claims or inconsistent updates |
| Reusable state | Section-three questions reuse each respondent's original state without replaying earlier sections; deliberate history removal is visible |
| Question independence | Mixed typed questions retain answer identity and receive identical pre-group state without sibling leakage, including after splitting/recovery |
| Source evidence | Offered choices resolve to exact authored text and feed another request through reusable references |
| Inspection and selection | Same resolution semantics as execution; current match/completeness facts are honest; acceptance freezes the actual selected set |
| Controlled deletion | Dry run changes nothing; deleting a source leaves retained follow-ons valid; explicit scope governs dependent deletion |
| Interpretation boundary | MCP exposes useful structured evidence; shipped skills enable the agent to query, interpret and compose without prescribed verdicts |
| Installed runtime | Supported Codex installation can perform these operations using the packaged runtime and persistent data configuration |

Release readiness requires the complete section-three workflow and supported typed journey capabilities. Supported matched-arm/run comparisons retain their declared meanings; legacy tool and storage formats need not remain compatible. Provider evidence and paid smoke authorization remain distinct from automated Sheg integration tests.

## 12. Roadmap and JIT planning contract

The approved capability sequence is:

| Checkpoint | Linear ownership | Exit capability |
| --- | --- | --- |
| Durable requests | SHEG-5 | Ask one question, leave the chat, discover and retrieve it later; lifecycle and deletion remain orderly |
| Reusable evidence | SHEG-7 | Query results and submit follow-ons using exact respondent/turn/context references |
| Richer questions and material choices | SHEG-6 and SHEG-8 | Independent typed groups and exact source-linked selections operate over new and reused contexts |
| Release integration | Across the active issues | Packaged tools/skills deliver the complete section-three investigation |

Skills develop with each checkpoint, not only at the end. The roadmap may divide an issue into consecutive plans when its runtime, contract, and persistence seams need smaller deliverables. Four issue identifiers do not imply four enormous plans.

After specification approval, write a roadmap of capability checkpoints and the first bounded implementation plan. Write each later plan only when its preceding checkpoint provides current code, contracts, and evidence. Do not pre-author all implementation tasks or speculative provider adapters from this epic.

Each JIT plan must name its user-visible exit, scope, prerequisites, source seams, relevant ADR work, breaking changes, focused proof, and remaining release gaps. Implementation-owned choices include exact tool names/JSON syntax, projection and filter representation, SQL schema/driver, worker topology, ownership protocol, batching algorithms, identifiers/fingerprints, storage-version/reset mechanics, and submission-key retention. They must satisfy this spec's semantic contracts.

If choosing one would change user authority, data custody, privacy, paid-work authorization, accepted behavior, or release scope, return the concrete decision for human review rather than burying it in a plan. Provider/harness feasibility work belongs in the affected JIT plan and cannot silently weaken acceptance.

Feature work uses canonical isolated worktrees based on current `origin/develop` and PRs target `develop`. Preserve pre-existing work. Run `npm run verify` before publication and regenerate/check canonical projections when affected. Feature plans preserve aligned version fields. Release preparation owns `release/0.3.0`, promotion to `main`, version/tag alignment, GitHub plugin ZIP publication, and reconciliation to `develop` under the repository release workflow.
