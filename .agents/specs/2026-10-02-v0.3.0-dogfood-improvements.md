## 1. Journey topology and context

Sequence and graph are forms of one journey model. Sequence remains a convenient shorthand for the existing all-items-then-tasks order, compiled into a linear graph. A staged linear reading journey can use explicit interleaved expose/ask nodes without branching. Switching topology must not silently change the material-memory policy.

Previously exposed material remains available by default, consistently for sequence and graph. Never include unexposed items or text from another branch. Retain exact supplied text and a deterministic material order. Re-exposure must not create accidental duplicate prose or change its source identity; exposure events still record each occurrence.

Material scope and prior-answer inclusion are distinct choices. Preserve the existing task-level `responseHistory: include | omit` contract where possible; new skill-authored dependent questions state this choice explicitly. Do not use one overloaded history boolean for both earlier prose and earlier answers. Keep exposure evidence inspectable even when prior responses are omitted from the provider packet.

An isolated-passage follow-on explicitly selects its material and omits earlier context. A cumulative journey is an intelligible packet contract, not a claim to simulate human recall fidelity. Context-fit inspection and runtime checks must use the same packet assembly, including the additional cumulative text. Overflow must remain explicit; never silently trim material or history.

Acceptance: equivalent sequence and linear-graph requests produce equivalent respondent-visible material and response-history state at corresponding questions. A branch never leaks unexposed material. Durable recall, resume, preview, preflight and execution agree about packets. Existing frozen runs retain their original packets and compiler identity rather than being reinterpreted under a new default. Record the contract change in a new ADR and update the index.

## 2. Unexpected-outcome diagnostics

Tell the agent exactly which observed contract failed. Typed validation reasons include malformed answer shape, answer-type mismatch, unknown option, incorrect probability keys, invalid probability sum, score outside its rubric, and score legend mismatch. Preserve question/evaluation and physical-attempt identity. Where safe, include field path, expected constraint and bounded observed information.

Separate observed failure from guessed provider cause. Never expose credentials or dump raw provider responses. Explain whether dispatch happened, whether an attempt was charged or uncertain, which sibling answers survived, and whether the failure stopped the run. Recovery guidance must derive from actual run state and remaining allowance rather than treating every invalid answer as retryable.

Acceptance: a malformed answer in a mixed group returns a precise safe reason while successful siblings remain readable. The same reason survives persistence, attempts/answers views, query and resume. A run-scoped failure and a respondent-local failure remain distinguishable. Existing behavior tests should be extended only where they lack genuine coverage; no tests that merely check rewritten wording.

## 3. Reuse selected stimulus as next stimulus

The agent can select recorded answers from one source run and request that each respondent receive the exact stimulus linked to their own choice. One follow-on run handles differing material selections. Sheg resolves saved mappings; it does not infer relevant passages or choose the next question.

Example: show a pull quote and seven paragraphs, ask which paragraph best expresses the quote, then show each selecting respondent only their selected paragraph and the shared pull quote. Ask how clearly that paragraph expresses the quote without the surrounding article. The first judgment is relative selection; the second is adequacy in changed context.

The next request supplies questions, source selection and explicit context semantics. It can combine respondent-specific selected stimulus with explicit shared material such as the pull quote. Earlier article text and answers are absent in the isolation mode. Material used by other respondents is absent. Continued-answer context remains an explicit separate option.

Only answered mapped Choice selections qualify. Report no-fit/unmapped answers, failed/pending selections and resulting coverage explicitly; never silently invent a passage or treat excluded rows as negative responses. Freeze the resolved material, exact handles, source/text digests and lineage at acceptance. Keep accepted follow-ons independently readable after source deletion. Preserve source-version race detection and submission idempotency.

Acceptance: Alice and Carol selecting paragraph 3 and Bob selecting paragraph 7 yield one run with three correct packets, one shared question and no cross-respondent material leakage. No-fit selection has explicit exclusion evidence. Independent sibling selections do not accidentally duplicate a respondent's follow-on context. The final request field names and generated schemas are specified in the owning implementation plan against the delivered context code.

## 5. Lifecycle and development identity

### Lifecycle

The current query marker `sourceComplete` means only `sourceStatus === completed`. Replace its ambiguous public role with explicit execution, coverage and recovery information. A stopped partial run must not imply more work will happen automatically. Preserve detailed statuses `prepared`, `running`, `completed`, `partial`, `failed`, `cancelled` and `interrupted`, with an unambiguous account of their consequences.

Reads can reconcile expired ownership but never start or resume work. Report answered, failed, pending and unreached counts accurately. Query-wide coverage and coverage for the selected question are different denominators; a failed unrelated sibling must not make all selected answers appear missing. Recovery eligibility and refusal reasons must agree with `run_resume`, uncertain/reserved attempts, cancellation and original call allowance. Paginated query snapshots must identify their captured state so they cannot be mistaken for fresh live status.

Acceptance: a stopped run with all 72 selected reading-choice answers and one failed sibling reports that execution stopped, the selected evidence is available, and any retry requires explicit resume. Inspection, query, status, follow-on warnings, persisted lineage and generated contracts agree. Define the exact public lifecycle projection in its implementation plan; do not add independently maintained contradictory booleans.

### Explicit recovery of respondent-local journey failures

An author can explicitly resume a partial journey when a respondent-local failure leaves a known failed turn, no attempt is unresolved, cancellation is not pending, and the original provider-call allowance has room. Resume preserves completed answers, frozen packets, respondent-specific exposure/response history, route choices, reached-turn order and physical-attempt history; it retries only eligible failed turns and continues each respondent from the saved checkpoint. A valid retry may determine the next branch, which is reached only after that answer succeeds. Retries consume the original remaining allowance and never replay completed work or increase the run limit. Cancellation, exhausted allowance, unresolved attempts and missing retryable work produce accurate refusal reasons. Run-scoped and interrupted recovery behavior remains explicit and unchanged unless required to keep the shared transition safe.

Acceptance: a respondent that fails on a reached turn after answering an earlier branch resumes under the same run ID, retains its previous answers and path, and dispatches only the failed turn before continuing from the new valid response. A respondent that completed another path is not called again. The saved packet and compiler identity are unchanged; earlier failed physical attempts remain inspectable; a retry failure remains partial; and actual resume eligibility agrees with the status/query lifecycle projection.

Development checkpoints use `<target>-dev.<n>`; prepared release candidates use `<target>-rc.<n>`; stable promotion uses `<target>`. Increment at intentional checkpoints, not every commit. Keep all version sources aligned. Local packaging accepts the approved prerelease forms without a tag. Stable release tagging/publication remains `vMAJOR.MINOR.PATCH` on verified main; prerelease tags do not bypass that gate.

Preserve reproducible copied packages and generated consistency checks. Record installed runtime/skill identity in dogfood evidence using package version plus exact artifact/source evidence. Do not use commit-dependent generated files that change at every documentation commit or invent a source SHA in the staged snapshot, which has no Git checkout.

Acceptance: an extracted candidate package initializes its MCP as `0.3.0-dev.2` without checkout or dependencies. Candidate packaging succeeds without a tag, while a stable-tag validation against dev manifests fails. Existing stable-tag mismatch/retargeting protections remain covered. Add a superseding version-policy ADR rather than rewriting ADR-0013's historical decision.

## 6. Skill scenario testing

Add maintainable behavior scenarios owned by the skills under `skills/<name>/tests/behavior/`. Packaging checks remain separate from tests of an agent following guidance. The current suite has packaging/link checks but no repeatable fresh-agent pressure suite.

Use realistic user requests and controlled MCP responses. The actor receives the actual candidate skill and realistic runtime framing, not the expected answer or evaluator rubric. Capture its requests, actions and final interpretation. Evaluator-only criteria judge observable behavior rather than phrase matching or self-reported compliance. Control tools so scenarios cannot dispatch paid inference, message people or modify real study data.

Initial cases cover interleaved exposure and cumulative context, independent versus dependent questions, selected-stimulus isolation with a no-fit selection, a stopped partial source with complete selected-question evidence, precise invalid-answer recovery, and comparison pressure to overstate a changed rubric. Start with a small demonstrated set, not a task-size matrix.

Before changing skill behavior, run the relevant scenario against the current guidance; retain successes as protection. For a suspected guidance failure, use a no-guidance control and observe a genuine failure before expanding prose. Compare old and candidate guidance against fixed scenarios; repeat at least five fresh-context trials for behavior-shaping wording and manually inspect each flagged result. Keep scenario changes versioned and explain intended contract changes instead of relaxing criteria to green a run.

Separate deterministic fixture/evaluator checks in `npm run verify` from explicitly invoked fresh-agent scenario campaigns. A campaign reports scenario version, skill identity, actor runtime/model settings, trial count, tool trace, verdict and harness limitations. A fixture replay proves the fixture/evaluator, not live agent behavior. Add new scenarios when dogfooding reveals another useful boundary.

## 7. Native TypeSafe inference is a v0.3.0 release requirement

The native `typesafe/jev-latest` route must pass Sheg admission and complete a real study using the stored credential before v0.3.0 is released. The implementation must use an evidence-backed context-fit policy based on TypeSafe's own documentation and supported API behavior. Current TypeSafe model documentation describes Jev 1.13 as supporting 64k total request context and 32k for state plus the longest question; the implementation plan must translate those documented limits into a conservative bound for Sheg's actual serialized native request, estimator and headroom. Reconfirm the official model documentation and the `jev-latest` target before stable release. Do not borrow OpenRouter's limit by assumption, weaken or bypass admission, or allow an unverified native route to dispatch.

Automated coverage must meaningfully exercise native fit and overflow admission, refusal before dispatch, secure authentication routing, typed answers, provider/model identity, physical-call accounting and safe failures. Live acceptance uses the stored credential for a real native TypeSafe study and a realistic author follow-up on a Portfolio article, then verifies durable recall after reopening or reconnecting. Live outputs and receipts remain outside the repository. Paid validation is authorized for an initial 500 API calls; request more authorization before exceeding that amount. This extends the earlier planning boundary for this specific native-validation work.

## 8. Datastore upgrades are safe from the v0.3.0 release baseline onward

Development prerelease datastores may be discarded; no migration guarantee applies before v0.3.0. The final v0.3.0 candidate establishes the first supported SQLite schema baseline. Every later schema-changing plugin update must migrate from each supported prior schema without losing accepted requests, frozen context packets, typed answers, material lineage, physical attempts or call accounting. Migrations are sequential, transactional and data-preserving, with a verified pre-migration backup and integrity checks. Evolving persisted JSON contracts are versioned and upcast explicitly where needed; frozen historical evidence is not silently reinterpreted. Never automatically reset data after a migration failure or when encountering a newer unsupported schema.

If datastore opening or migration prevents normal startup, the MCP still exposes a bounded maintenance/recovery surface for compatibility status and safe export or explicitly confirmed reset. Ordinary study tools refuse writes until recovery succeeds. A migration failure leaves the original data recoverable and gives the user a usable next action. Supersede ADR-0018 with this release boundary and supported-schema policy.

The 0.3.0 release gate includes source-owned fixtures for the baseline and supported migration inputs, automated proof that every migration preserves data/accounting, rollback on failure, no mutation for unknown future schemas, and usable maintenance access after normal startup fails. Future schema changes require their migration and upgrade tests in the same change. Fixtures are test code; run results and development receipts stay outside the repository.
