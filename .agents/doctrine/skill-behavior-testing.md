# Skill behavior testing

Sheg skills are behavior-shaping source. Keep scenarios, evaluators, calibration examples, and behavior tests under the owning skill's `tests/behavior/` tree. Keep live campaign outputs, raw actor/judge results, reports, and run databases transient and outside the repository; inspect them during development, then discard them after review. Never commit run results or receipts as skill tests. The packaged plugin ships guidance but excludes skill tests. Shared harness implementation belongs in `scripts/skill-testing/`; deterministic harness tests belong in `test/skill-testing/`.

Never run skill behavior scenarios or campaigns in CI or the pre-commit hook. `npm run verify` may test the shared campaign machinery with deterministic fixtures and fake adapters, but it must not dispatch skill actors or judges or claim a skill-behavior result. The existing scenario harness unit tests validate catalog pairing, prompt boundaries, trace schemas, and fixture contracts; they do not run the skills against scenarios. A new catalog entry does not automatically gain live campaign coverage.

Use `npm run skill:campaign -- prepare --config <file> --output <off-repository-directory>` to freeze scenario request/evidence, evaluator criteria, guidance snapshots/references, execution settings, and (for workflow suites) ordered user turns and private checkpoint expectations. The manifest retains the contents as well as hashes. Comparison requires matching request, evidence, rubric, suite, classification, repetitions, and execution settings. Actor prompts contain only the selected guidance and the current request/evidence. Workflow prompts expose Sheg MCP availability without directing the actor to a specific call; future turns and expected tool checkpoints are withheld until their intended role as later user turns or evaluator inputs.

Run or resume with explicit `--backend codex`. Discovery outputs have a distinct JSON contract containing the selected skill or null and a rationale; they are not parsed as focused actor traces. The Codex adapter uses bounded concurrency, short stable scratch paths, fresh ephemeral focused/discovery sessions, and a persistent per-trial workflow session resumed by its exact session ID. Live workflow actors can and should call the configured Sheg MCP tools when a scripted turn requires them. Before dispatch, the adapter reads the enabled stdio Sheg server configuration and overrides the complete server definition so both `PLUGIN_DATA` and `SHEG_DATA_DIR` point into that attempt's working directory; this matters because the configured plugin data path can take precedence over a process-level `SHEG_DATA_DIR`. If the Sheg server cannot be resolved as an enabled stdio server, dispatch fails closed. After capture, the per-attempt Sheg store is copied under that attempt for inspection. Tool availability remains ambient; this is data isolation, not tool isolation. The adapter captures raw event streams, final text, stderr, requested and observed settings, and append-only attempt records. A captured trial is not dispatched again. Runtime errors remain separate from behavior results; a behavior rerun gets a new trial identity. The fake adapter is for deterministic tests only. Live executions are absent from `npm run verify`.

Focused outputs are checked against the actor trace contract and the exported Sheg `runRequestSchema` for executable `run_inspect`/`run_start` proposals. These checks distinguish plausible prose from invalid requests; incomplete design replies are not forced into executable requests. `grade --backend codex` sends retained actor output and the frozen rubric to a separate fresh judge context without an arm label, saves its raw outputs, and validates criterion-level pass/fail/uncertain judgments with evidence. Workflow judgments also receive raw Codex events and hidden checkpoint expectations. Expected Sheg MCP calls are checked deterministically against `item.started` events from the `sheg` server; actor claims and semantic judgments alone cannot satisfy a tool checkpoint. Judge failures stay uncertain and are not converted into behavior failures. `report` emits JSON, Markdown, and escaped static HTML with trial counts, failure categories, missing actor/judge model metadata, raw-output links, and explicit unavailable usage/timing fields.

`compare --baseline <dir> --candidate <dir> --backend codex` first rejects changed comparison inputs, then pairs captured repetitions. A stable hash assigns anonymous A/B labels; two separate judge runs see the same labels in reversed display order. The harness retains both judgments, disagreements, and a separate empty human-adjudication field. It does not provide a command for entering or resolving adjudication, and small-sample outcomes do not imply statistical significance or general reliability.

Calibration fixtures include good, bad, and borderline examples with expected criterion labels and rationale. The current agreement helper reports disputed criteria but does not enforce a minimum score or run a full calibration campaign. Keep articulate invalid requests and unsupported claims among the calibration cases. Judges should cite observed evidence rather than match phrases.

Before changing guidance, select affected capability cases and shared regression safeguards. Compare frozen old and candidate guidance under identical request, evidence, criteria, and execution settings. Use no-guidance only as a separate attribution control. Include relevant discovery near-misses, changed-follow-up workflow cases, and held-out wording where available. Choose repetitions for the risk and record the rationale. Inspect all failures, uncertain judgments, missing metadata, and judge disagreements; never overwrite a failed trial or historical evidence.

Use `npm run skill:campaign -- select --owner <skill>`, `--tag <tag,...>`, or `--guidance-path <path,...>` to find affected scenarios. Filters combine across dimensions and match any supplied tag or path within a dimension. Add `--include-shared` to include scenarios tagged `shared-safeguard`; the output reports the scenario IDs, tags, and guidance paths to carry into campaign configs. Campaign comparison output includes per-criterion baseline counts, candidate counts, and candidate-minus-baseline deltas.

Tool isolation and universal tool-use auditing are ambient runtime concerns, separate from Sheg's harness. Workflow pressure tests should call Sheg MCP tools when the frozen checkpoint requires them, and the harness should preserve and grade the observed CLI events. Raw Codex events can show tool activity observed in that CLI stream; they do not prove universal tool isolation or the absence of tools outside that stream. Do not add permanent hooks, telemetry, or tool isolation to Sheg.

Run `npm run verify` before publishing. It is a code-quality and deterministic behavior gate, not a live skill-campaign gate. Keep behavior tests out of customer plugin packages. Live campaign output, reports, and data stores are transient development artifacts: review them during the campaign and discard them rather than committing receipts.
