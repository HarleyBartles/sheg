# Provider selection and comparison controls

Sheg can pin one provider for an entire request or choose a provider for each eligible unit. The agent designs the study and may leave the operational choice to Sheg; a provider pin, preference, required capability, or comparison lock is a study-design choice and should be included only when it serves the research question.

Every request must set exactly one of `provider` or `providerSelection`. An explicit `provider` holds one provider configuration across the request. To ask Sheg to choose, omit `provider` and set `providerSelection: {}`. Automatic selection requires a provider catalogue entry that is enabled, configured, ready, supports the question type and required input capabilities, fits the full packet, and fits the remaining call allowance. A pixel-bound question requires pixel capability and therefore selects an eligible Clef entry.

Sheg applies the agent's unit pin first when that provider remains eligible. Otherwise it honors the request's `preferredOrder`, then the user's saved `preferredOrder`. With neither preference, Sheg prefers an eligible local provider that has no provider invoice; among hosted providers with comparable published pricing it chooses the lowest estimated cost. If pricing is missing or currencies cannot be compared, the estimate stays unknown and Sheg uses stable catalogue order. Fit estimates and price estimates are advisory evidence, not guarantees of actual billing or model quality.

Use `providerSelection.unitOverrides` to pin a respondent/question unit. Use `providerSelection.comparisonLocks` to keep multiple authored comparison members on the same provider and model, or intentionally vary one of those dimensions. A provider or model change is part of the treatment: when comparing respondents or stimuli, hold the model constant unless the study intentionally tests provider or model effects. A capability requirement can make that impossible; state it in the interpretation.

Automatic follow-on requests choose a provider per selected source context. A follow-on `comparisonLocks` declaration is rejected for now because respondent/question references do not uniquely identify frozen source contexts. Pin one provider for the entire follow-on or omit the lock.

Sheg plans grouped calls and splits questions when a provider's fit requires it. Set `providerSelection.batching` to `singleton` when separate physical calls are part of the design. Sibling answers still do not appear in one another's context. The `maxCalls` limit counts physical provider attempts, including split calls and retries.

Automatic-routing inspection reports `initialChoices` with selected provider and model identity, decision reason, candidate fit, readiness/capability exclusions, preferences, comparison locks, and known or unknown cost evidence. It also reports `unresolvedFutureJourneyUnits` for later ask nodes whose respondent-specific packet does not exist yet. Sheg chooses those units again when reached, after prior answers and exposures are known, and records the provider and served model in run evidence. `run_query` shows the provider execution attached to each answered unit.

Read current settings through `provider_settings` in MCP or with a CLI JSON request containing `{"operation":"get"}`. Replace settings with `{"operation":"set","expectedRevision":N,"catalogue":{"entries":[...]},"preferences":{"preferredOrder":[...]}}`; use the exact revision returned by the previous read. Credential values are never part of settings requests or responses. Configure and remove provider secrets with `provider_credential` or `provider-credential`, which uses the secure credential workflow.

For image-backed Choice options, map only stable option IDs to image material IDs that are bound to the same question with `visual.mode: "pixels"`. Option mappings establish visual option identity in the provider packet; an image choice does not become text `selectedMaterial` evidence. See [Native Cloudflare Clef](clef.md) for import, scaling, and image limits.
